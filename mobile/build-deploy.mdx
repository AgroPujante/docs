## app.json

Configuração central do app Expo:

| Chave | Valor |
|---|---|
| `scheme` | `agropujante://` |
| Bundle ID (iOS) | `com.agropujante.mobile` |
| Package (Android) | `com.agropujante.mobile` |
| Plugins | `expo-router`, `expo-secure-store`, `expo-font`, `expo-location`, `expo-web-browser`, `expo-notifications` |
| `expo.extra.apiUrl` | Base do AgroPujante `/api/v1` |
| `expo.extra.escolaApiUrl` | Base da Escola `/api/v2` |

<Note>
  Desde o upgrade pro SDK 57 (2026-09-15), `expo-image`, `expo-sharing` e `expo-splash-screen` já expõem config plugin de verdade e entram na lista de `plugins` do `app.json` normalmente (o `splash` legado no topo do `app.json` foi removido — SDK 57 não aceita mais essa chave, virou config do plugin `expo-splash-screen`). `expo-linear-gradient` continua sem plugin e funciona só via autolinking.
</Note>

## EAS Build

EAS já está configurado: `expo.extra.eas.projectId` no `app.json` aponta pra um projeto real, e `eas.json` define os profiles `development`/`preview`/`production` (iOS `ascAppId` e Android `serviceAccountKeyPath` já preenchidos pro submit).

<Note>
  O app roda em **Expo SDK 57** (upgrade de 54→57 em 2026-09-15, `react-native` 0.81.5→0.86.3, `react` 19.1.0→19.2.3). `react-native-reanimated`/`react-native-worklets` foram bumpados além da versão baseline do SDK 57 (4.6.0/0.12.x) pra satisfazer o peer dependency de `react-native` 0.86 — listados em `expo.install.exclude` no `package.json` pra `expo install --fix` parar de reclamar. `@react-navigation/native` como dependência direta foi removido: desde o SDK 56, `expo-router` embute sua própria cópia do react-navigation e ter o pacote direto no projeto quebra o bundle ("expo-router is no longer compatible with react-navigation") — trocar qualquer `useFocusEffect`/hook equivalente pelo export do próprio `expo-router`.
</Note>

O desenvolvimento roda via **Expo Go** (com a Escola apontando pro IP da rede local) e `npx expo start`, exceto para push notifications — ver aviso abaixo.

<Warning>
  O Expo Go publicado na App Store/Play Store só suporta a versão mais recente do SDK — se ainda não tiver sido atualizado pro SDK 57, o QR code do `npx expo start` é recusado com "Project is incompatible with this version of Expo Go". Nesse caso, usar um **development build** (`eas build --profile development`) em vez de Expo Go.
</Warning>

## Deep links

O scheme `agropujante://` abre o app direto nas rotas suportadas:

- `agropujante://post/[slug]` — leitor de post
- `agropujante://autor/[slug]` — página do autor
- `agropujante://coluna/[slug]` — página da coluna

São usados em notificações push e compartilhamento.

## Push notifications

O app usa o serviço de push do **Expo** (`expo-notifications`), com registro/desvínculo de token feitos automaticamente pela store `notifications`. Device recebe push mesmo **sem login** — a conta só é usada pra vincular o token, não é pré-requisito.

<Steps>
  <Step title="Permissão">
    No boot do app (`syncPushToken`), independente de login, o app pede permissão de notificações ao usuário.
  </Step>
  <Step title="Token Expo">
    Com a permissão concedida, obtém o Expo push token do device via `Notifications.getExpoPushTokenAsync` (usa o `projectId` do EAS).
  </Step>
  <Step title="Registro no backend">
    Envia `POST /push-tokens` com `{expo_push_token, platform}` pro backend do Portal — grava (upsert por token) na tabela `pujante.mobile_push_tokens`. Auth é opcional: com sessão, vincula `user_id`; sem sessão, salva como anônimo (`user_id null`) e o device continua recebendo push de conteúdo geral.
  </Step>
  <Step title="Desvínculo no logout">
    No logout (`detachOnLogout`), re-registra o mesmo token forçando `auth: false` (em vez de apagar) — o device volta a ser anônimo mas continua recebendo push depois de sair da conta.
  </Step>
</Steps>

<Warning>
  **Expo Go não suporta push remoto desde o SDK 53.** O registro de token roda normalmente (o app só loga um warning e segue), mas pra validar o recebimento de push de verdade é preciso um **development build** (`eas build --profile development` ou `expo run:ios`/`expo run:android`), não Expo Go.
</Warning>

<Note>
  Disparo de push (Fase 2) está em produção desde 2026-09-17: `app/services/mobile_push.py` (backend) dispara automaticamente ao publicar conteúdo novo (`notify_if_newly_published`, hookado em `posts.py`), filtrando destinatários por `mobile_push_tokens.categorias` (default: todas habilitadas). Ver [API consumida](/mobile/api-consumida) pra detalhes do endpoint.

  Esteve pausado (comentado no código, `_spawn_send_mobile` desligado) de 2026-09-10 a 2026-09-17 — a linha ficou comentada em `main` mesmo depois do PR de reativação ter sido aberto em 2026-09-15, só entrou em produção quando o PR ([#500](https://github.com/AgroPujante/AgroPujante/pull/500)) foi de fato mergeado e deployado em 2026-09-17. `push_notified_at` continuou sendo carimbado normalmente durante toda a pausa (é o web push que carimba), então religar não reenviou push mobile pros posts publicados nesse meio-tempo — e esse carimbo por si só não prova que o push mobile disparou, já que também é setado quando só o web push roda.
</Note>

<Note>
  **Credencial APNs confirmada OK em 2026-09-17.** O problema achado em 2026-08-21 (Expo aceitava o envio com HTTP 200 mas o ticket vinha `status: error` / `InvalidCredentials` por falta de chave push pro bundle ID) foi resolvido. Testado com push silencioso (`contentAvailable`, sem alerta) em 3 tokens iOS reais de produção: `send` retornou `status: ok` e `getReceipts` (~16min depois) confirmou `status: ok` — a Apple confirmou a entrega.
</Note>

<Warning>
  **Regressão: sem checagem de status por ticket desde 2026-08-27.** O commit `c8b4e2f` (fix de tag HTML crua no título) reescreveu `mobile_push.py` e removeu, sem avisar no commit, a checagem de `data[i].status`/`details.error` por ticket da Expo e a poda automática de tokens com `DeviceNotRegistered` — lógica que tinha sido adicionada em `34611e7` (o próprio commit que descobriu o problema de credencial acima). Hoje o código só confere o HTTP 200 do POST pra Expo e conta como "enviado" — se a credencial quebrar de novo ou algum ticket falhar, não vai gerar log nem erro visível, só vai parecer que enviou sem nunca chegar no aparelho. Reaplicar a lógica de `34611e7` em `_send_to_tokens` (`mobile_push.py`) resolveria isso.
</Warning>

## Carregamento de imagem

Os componentes que renderizam imagem remota (capas de post, avatares de autor, logos de apoiador/parceiro etc.) usam `expo-image` em vez do `Image` nativo do React Native — dá cache automático em disco/memória (imagem já vista carrega instantânea) e transição de fade-in (`transition={200}`) em vez de "pop" abrupto quando a imagem termina de carregar.

<Note>
  Ainda não há redimensionamento no servidor — um avatar de 32px carrega o arquivo original em resolução cheia do Supabase Storage. Uma fase futura pode usar o endpoint de transformação de imagem do Supabase (`/render/image/public/...?width=&height=`) pra pedir só o tamanho necessário por contexto, mas depende de confirmar se Image Transformations está habilitado no plano do projeto.
</Note>

## Pendências

Itens conhecidos antes de um release de produção:

<AccordionGroup>
  <Accordion title=".env por ambiente">
    As base URLs vivem hardcoded em `expo.extra` no `app.json`. Falta um esquema de variáveis por ambiente (dev/staging/prod) — por exemplo via `app.config.ts` + `.env`.
  </Accordion>
  <Accordion title="Refresh token">
    Não há refresh automático da sessão do Portal: token expirado força novo login (logout silencioso no 401). Veja [Autenticação](/mobile/autenticacao).
  </Accordion>
  <Accordion title="Checagem de status por ticket da Expo (removida)">
    Desde `c8b4e2f` (2026-08-27), `mobile_push.py` não confere mais `data[i].status`/`details.error` por ticket — só o HTTP 200 do POST pra Expo. Uma falha de entrega por ticket (credencial inválida, device removido) não gera log nem erro visível, e tokens com `DeviceNotRegistered` não são mais podados automaticamente. Ver nota acima.
  </Accordion>
</AccordionGroup>

<Note>
  Nenhum valor de chave ou secret deve ser commitado no `app.json` ou em arquivos versionados — apenas URLs públicas e identificadores de bundle.
</Note>
