title: "API: Gantt"

---

O Gantt do Pujante Admin organiza o trabalho do time na hierarquia **Time &gt; Projeto (macro) &gt; Pessoa &gt; Task (sub)**. Os dados vivem no schema configurado por `GANTT_SCHEMA` (tabelas `gantt_teams`, `gantt_persons`, `gantt_macros`, `gantt_subs`, `gantt_macro_members`, `gantt_events`).

Todos os endpoints exigem **JWT Bearer** — API keys não têm acesso ao Gantt.

<Note>
A URL base `https://admin-api.pujante.com.br` usada nos exemplos é **ilustrativa** — a base real depende do deploy no Railway.
</Note>

## Erros comuns

Shapes padrão do FastAPI, válidos para todos os endpoints desta página. Os exemplos por endpoint referenciam esta seção em vez de repeti-los.

```json title="401 Unauthorized — sem credencial"
{ "detail": "nao autenticado" }
```

```json title="401 Unauthorized — JWT inválido ou expirado"
{ "detail": "token invalido: Signature has expired" }
```

```json title="403 Forbidden — email fora de ALLOWED_ADMIN_EMAILS"
{ "detail": "usuario nao autorizado" }
```

Caso específico do Admin: API key tentando um método de **escrita** (POST/PATCH/DELETE) — a chave é read-only e nunca passa em escrita:

```json title="403 Forbidden — API key em método de escrita"
{ "detail": "API key e somente leitura — apenas requisicoes GET sao permitidas" }
```

```json title="422 Unprocessable Entity — validação de body/params"
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "title"],
      "msg": "Field required",
      "input": {}
    }
  ]
}
```

## Regras de negócio

<Accordion title="Status e status_dates automáticos">
Macros e subs têm status `todo` (padrão), `progress`, `done`, `blocked` ou `postponed`. Ao mudar o status via `PATCH`, o backend aplica automaticamente as `status_dates` (data de início real ao entrar em `progress`, data de conclusão ao entrar em `done`). Você não gerencia essas datas manualmente — valores enviados explicitamente prevalecem.
</Accordion>

<Accordion title="Só o dono conclui">
Apenas o **dono** da macro/sub — a pessoa registrada em `requested_by_id` (quem pediu a entrega) — pode mover o item para `done`. A verificação é feita pelo e-mail do usuário logado contra o e-mail da pessoa em `requested_by_id`; outros usuários recebem **403** ao tentar concluir.
</Accordion>

<Accordion title="Hierarquia Time > Projeto > Pessoa > Task">
Times agrupam projetos (macros). Cada macro tem um líder (`person_id`) e pode ter membros adicionais. Subs (tasks) pertencem a uma macro e a uma pessoa. A árvore retornada por `/gantt/tree` reflete essa hierarquia, ordenada por `sort_order`.
</Accordion>

### POST /gantt/macros

<ParamField body="title" type="string" required>
Título do projeto.
</ParamField>

<ParamField body="description" type="string">
Descrição.
</ParamField>

<ParamField body="start_date" type="string" required>
Data de início planejada (`YYYY-MM-DD`).
</ParamField>

<ParamField body="end_date" type="string" required>
Data de fim planejada (`YYYY-MM-DD`).
</ParamField>

<ParamField body="status" type="string" default="backlog">
`backlog`, `progress` ou `done`.
</ParamField>

<ParamField body="team_id" type="string" required>
Time dono do projeto.
</ParamField>

<ParamField body="person_id" type="string" required>
Líder do projeto — única pessoa que pode movê-lo para `done`.
</ParamField>

<ParamField body="requested_by_id" type="string">
Pessoa que solicitou o projeto.
</ParamField>

<AccordionGroup>
<Accordion title="POST /gantt/macros">

```bash title="Requisição (JWT)"
    "start_date": "2026-06-01",
    "end_date": "2026-07-15",
    "status": "progress",
    "team_id": "t_5a6b7c8d",
    "person_id": "p_1a2b3c4d",
    "requested_by_id": "p_0d1e2f3a"
  }'
```

```json title="201 Created"
{
  "id": "m_9f8e7d6c",
  "person_id": "p_1a2b3c4d",
  "team_id": "t_5a6b7c8d",
  "title": "Portal do Professor",
  "status": "progress",
  "start_date": "2026-06-01",
  "end_date": "2026-07-15",
```

<Accordion title="PATCH /gantt/macros/{id}">
Mover para `done` dispara a **trava de conclusão**: o backend busca o e-mail da pessoa em `requested_by_id` (quem pediu o projeto) e compara com o e-mail do JWT logado.

```bash title="Requisição (JWT) — concluir o projeto"

  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \

```

```json title="200 OK — actual_end preenchido automaticamente"
{
  "id": "m_9f8e7d6c",
  "person_id": "p_1a2b3c4d",
  "team_id": "t_5a6b7c8d",
  "title": "Portal do Professor",
  "status": "done",
  "start_date": "2026-06-01",
  "end_date": "2026-07-15",
  "actual_start": "2026-06-03",
  "actual_end": "2026-06-12",
  "sort_order": 0,
  "completion_note": "Entregue com as 3 telas previstas",
  "requested_by_id": "p_0d1e2f3a",
  "description": "Nova área de gestão de turmas na Escola"
}
```

Tentar concluir sem ser o dono (e-mail do logado ≠ e-mail de quem pediu):

```json title="403 Forbidden — só o dono conclui"
{ "detail": "Só Ana Beatriz (quem pediu) pode marcar como concluído." }
```

Dono sem e-mail vinculado em `gantt_persons` (não dá pra verificar):

```json title="403 Forbidden — dono sem e-mail vinculado"

```

```json title="400 Bad Request — body vazio"
{ "detail": "nada para atualizar" }
```

```json title="404 Not Found — id inexistente"
{ "detail": "não encontrado" }
```

Mudanças reais geram evento `updated` em `gantt_events` com diff `{from, to}` por campo. Erros 401/403/422: veja [Erros comuns](#erros-comuns).
</Accordion>

## Events (timeline)

| Método | Path | Descrição | Auth |
|---|---|---|---|
| GET | `/gantt/events` | Timeline cronológica (mais recentes primeiro) de uma entidade | JWT |

<ParamField query="entity_type" type="string" required>
`team`, `project` ou `task`.
</ParamField>

<ParamField query="entity_id" type="string" required>
ID da entidade.
</ParamField>

<ParamField query="limit" type="integer" default="100">
Máximo de eventos retornados.
</ParamField>

<Note>
Os eventos são gravados em `gantt_events` a cada mudança relevante (criação, mudança de status, datas, atribuições), formando o histórico auditável do Gantt.
</Note>
